# ADR-0003：范围限定为显存可行性，不引入成本；instance 轴先行

- 状态：**Accepted**
- 日期：2026-08-31

## 决议

1. **不引入成本维度。** 不建模 $/小时、$/并发、$/token，也不建模供给可得性（region 覆盖、Capacity Blocks）。
2. **推进顺序：instance 轴 + provenance 先做**，model 轴排在其后；model 数据契约与 instance 轴同期抽出，但只填 Kimi K3 一个模型。

## 理由

instance 轴已被证明能改变结论（K3 从 4 台 p5en 变成 2 台 p6-b300），且能在单模型上验证正确性。model 轴需要 attention family 抽象，而该抽象在只有一个模型时无法验证——会为想象中的第二个模型设计错的接口。契约先抽出、只填一个，等真加第二个模型时缺陷立刻暴露，那时改比现在猜便宜。

## 后果：这个工具明确**不**回答什么

去掉成本之后，必须直说边界，否则会被误用：

- ❌ **不回答「p5en 还是 p6-b300 更值」。** 没有价格就没有「值」。
- ❌ **不回答「哪个 instance 吞吐更高」。** 工具只算显存，不算 FLOPS、不算带宽引起的延迟。b300 的 1.5× TFLOPS 和 2× 网络在模型里完全不出现。
- ✅ **回答「在某个 instance 上，这个模型最少要几台、每台怎么切、能收多少并发」。**

## 曾提议但被否决：把 hero 改成「最少实例数」

原提议：跨 instance 后「最大并发」退化成「显存越大越赢」，故主输出应改为最少实例数。

**该提议已否决**（见 ADR-0005：工具保持校验器，不做配置搜索）。最少实例数需要对每个候选台数枚举所有合法 `(TP, DP, PP, EP)` 组合并排序，排序函数需要一个价值判断，而成本维度已被移除，无法提供。

**代价很小**：`实例数` 本身就是一个下拉框，用户手动递增 1→2→3 直到 banner 变绿，二三次点击即可得到最少台数。校验器 + 可调实例数 ≈ 手动二分，因此放弃求解器几乎不损失可用性。

hero 保持为「当前上下文长度下的最大并发」。

## 未决

无。范围已锁定。
