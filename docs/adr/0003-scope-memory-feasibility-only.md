# ADR-0003：范围限定为显存可行性，不引入成本；instance 轴先行

- 状态：**Accepted**。「不回答吞吐 / 延迟」这一条，于 2026-09-15 被 [ADR-0010](0010-decode-roofline-lower-bound.md) 取代。成本 / 可得性这一条仍然有效。
- 日期：2026-08-31

## 决议

1. **不引入成本维度。** 不建模 $/小时、$/并发、$/token。也不建模供给可得性（region 覆盖、Capacity Blocks）。
2. **推进顺序：instance 轴 + provenance 先做。** model 轴排在其后。model 数据契约与 instance 轴同期抽出，但只填 Kimi K3 一个模型。

## 理由

instance 轴已被证明能改变结论：K3 的部署从 4 台 p5en 变成 2 台 p6-b300。instance 轴也能在单模型上验证正确性。

model 轴需要 attention family 抽象。只有一个模型时，这个抽象无法验证——会为想象中的第二个模型设计错的接口。

所以契约先抽出，但只填一个模型。等真的加入第二个模型时，接口缺陷会立刻暴露。到那时修复，成本比现在凭空猜测更低。

## 后果：这个工具明确**不**回答什么

去掉成本之后，必须直说边界。否则这个工具会被误用：

- ❌ **不回答「p5en 还是 p6-b300 更值」。** 没有价格就没有「值」。
- ❌ **不回答「哪个 instance 吞吐更高」。** 工具只算显存，不算 FLOPS、不算带宽引起的延迟。b300 的 1.5× TFLOPS 和 2× 网络在模型里完全不出现。
- ✅ **回答「在某个 instance 上，这个模型最少要几台、每台怎么切、能收多少并发」。**

## 曾提议但被否决：把 hero 改成「最少实例数」

原提议：跨 instance 比较后，「最大并发」这个指标会退化成「显存越大越赢」。所以主输出应改为最少实例数。

**该提议已否决**（见 ADR-0005：工具保持校验器，不做配置搜索）。最少实例数需要对每个候选台数，枚举所有合法 `(TP, DP, PP, EP)` 组合，并排序。排序函数需要一个价值判断。但成本维度已经被移除，无法提供这个判断。

**代价很小**：`实例数` 本身就是一个下拉框。用户手动把它从 1 递增到 2、3，直到 banner 变绿。两三次点击就能得到最少台数。校验器加可调实例数，约等于手动二分查找。所以放弃求解器，几乎不损失可用性。

hero 保持为「当前上下文长度下的最大并发」。

## 未决

无。范围已锁定。
