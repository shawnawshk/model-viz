# ADR-0005：保持校验器语义；instance 列表 per-model；dtype 不匹配提示

- 状态：**Accepted**
- 日期：2026-08-31

## 1. 校验器，不是求解器

工具接受用户手动给定的 `(instance, 实例数, TP, DP, PP, EP, 并发, 上下文, util)`，输出该组合是否可行及其显存构成。**不做配置枚举、不做排序推荐。**

理由：排序需要「哪个可行配置更好」的价值判断。候选目标函数互相冲突——「单卡余量最大」偏向低 TP 高 EP，「跨域通信最少」偏向 PP，而 PP 又有并发门槛。在成本维度被移除（ADR-0003）后没有可信的仲裁标准，工具不应替用户做这个判断。

代价见 ADR-0003：最少台数可由手动递增实例数在 2–3 次点击内得到。

## 2. instance 列表是 per-model 配置，不是全局工具范围

分两层，不要混：

**第一层 —— 规格总目录**：`docs/instance-specs.md` 收录 G5–G7 / P4d–P6 全部 57 个实例，以 `describe-instance-types` 的 MiB 为真值。它的作用是**参考与去重**：任何 instance 的规格都从这里查，不再每次去拉 API。目录本身不决定工具支持什么。

**第二层 —— 每个模型的候选 instance**：写在该模型的 json 里（`candidateInstances`），只列对这个模型有意义的机型。**建每个模型页面时逐个询问用户决定**，不由目录自动推导——「哪些机型值得为这个模型考虑」是业务判断，工具不该替用户做。

### 机型目录的排序约定

`data/instances.js` 的键顺序即下拉框顺序：**P 系优先，同系内越新越前；G 系在后。**

```
p6-b300 → p6-b200 → p5en → p5e → p5 → p4de → p4d → g7e → g7 → g6e
```

（G 系内部 `g7e` 排在 `g7` 前：两者同代，按容量/定位排，与 P 系「`p5en` > `p5e` > `p5`」同时也是越新越强的规律一致。）

### Kimi K3 的候选（2026-09-01 确认，4 个）

- `p5.48xlarge` / `p4de.24xlarge`：640 GiB/台，4 台勉强装下权重，但 MXFP4 kernel 生态不存在（p4de 是 Ampere，连 FP8 都没有）

### 两字段建模

目录中的 G 系三个机型满足「NVLink 域(1) < 每实例卡数(8)」，构成 ADR-0001 两字段建模的真实反例，因此 `gpusPerInstance` 与 `nvlinkDomainGpus` 必须分开，跨域判断为 `TP > nvlinkDomainGpus`。详见 ADR-0001 第二次修订。

**一个诚实的限定**：K3 的四个候选机型全部是「域 = 每实例卡数 = 8」，所以*在引擎的实际运行路径上*，这两个字段目前取值总是相同 —— 反例只存在于目录和索引页的机型表里，没有被 `compute()` 走到过。等某个模型把 G 系列为候选，这条路径才真正被验证。字段仍然分开（零成本、且判断已写成 `TP > nvlinkDomainGpus` 而非硬编码 8），但不要以为它已经被测过。

## 3. 权重格式可选 + dtype 三态提示（对 ADR-0003 范围的一次明确破例）

### 为什么权重格式必须可选，而不是写死

K3 的原生格式是 MXFP4（QAT 到 SFT 阶段），expert 权重实测 `0.53125 B/参数`。但 **Hopper 没有原生 FP4/microscaling**，引擎面对这个不匹配有两条出路，**显存后果相反**：

| 出路 | 显存 | 算力 |
|---|---|---|
| (a) 保持 4bit 在显存里，on-the-fly dequant 到 FP8 | 省下来了（1347 GiB） | 拿不到原生张量核，且 kernel 成熟度是风险 |
| (b) 直接把权重物化成 FP8 / BF16 | **也省不到了** | 拿到原生张量核 |

原实现只能表达 (a)，把 (b) 说成「显存省下来了」是**错的**。因此 expert 与非 expert 的权重格式都改为可选：

```js
expertFormats: [
  { id: "mxfp4", label: "MXFP4（原生）", bytesPerParam: null },  // null → 用 total_size 反解的实测值
  { id: "fp8",   bytesPerParam: 1 },
  { id: "bf16",  bytesPerParam: 2 },
],
nonExpertFormats: [ { id: "bf16", bf16Bytes: 2 }, { id: "fp8", bf16Bytes: 1 } ],
```

`bytesPerParam: null` 是关键设计：**原生格式走实测值，其余走推算**，两者的 provenance 级别不同（`推导` vs `估算`），表格里的标记与顶部边界声明都随之切换。

### K3 的实际差距（decision-relevant）

| expert 格式 | expert GiB | 权重合计 GiB | 4×p5en 128K 并发上限 |
|---|---|---|---|
| MXFP4（原生，实测） | 1347.1 | 1453.7 | **136** |
| FP8（推算） | 2535.8 | 2642.3 | **51** |
| BF16（推算） | 5071.5 | 5178.0 | **0（装不下）** |

BF16 在 4×p5en(4512 GiB) 与 2×p6-b300(4298 GiB) 上都装不下。**这不是边角情况，是选型结论会被推翻的量级。**

### 三态 banner

| expert 格式 | 机型原生支持 | 提示 |
|---|---|---|
| 原生 | 有 | **无提示**（理想组合，例如 p6-b300 + MXFP4） |
| 原生 | 无 | 警告：两条出路 + 显存后果相反 + 指路「切成 FP8 看 (b) 的账」 |
| 已重量化 | — | 警告：不是原生格式，字节数为推算；给出涨了多少 GiB 与百分比 |

### 仍然不建独立的 dtype 支持矩阵

`nativeDtypes` 内嵌在 instance 定义里，避免多一张需要同步的表。

## 4. 不做的事（防止范围回弹）

- 不算 FLOPS、不算吞吐、不算延迟
- 不算价格、不算 region 可得性、不算 Capacity Blocks 约束
- 不做配置推荐/排序
- 不支持第二个模型（契约抽出但只填 Kimi K3，见 ADR-0002）
